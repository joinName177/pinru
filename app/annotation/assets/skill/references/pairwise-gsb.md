# Pair-wise GSB 规则（09/16）

## 适用范围

一道题使用相同环境、相同完整 User Prompt 和相同模型配置独立运行两次，分别记为 A、B。每个 Session 只能有一轮有效交互，两次运行组成一条数据。旧版多轮五维评分不适用于本模式。

来源文档：`【初稿】CC用户反馈标注说明新规范.docx`，SHA-256 `08ff56fee0cccd1389ae71a8a675b2ed7fdbea205246a02482492c3c08e4e1ba`。平台提交页于 2026-09-17 实际核对。

## 提交字段

按以下顺序生成数据：

1. User Prompt
2. 任务类型
3. 任务难度
4. 语言/框架
5. Harness
6. Harness 版本
7. 操作系统
8. 环境可复现等级（选填）
9. 初始环境快照
10. A-SessionID
11. A-轨迹文件
12. A-产物快照
13. A-运行录屏
14. B-SessionID
15. B-轨迹文件
16. B-产物快照
17. B-运行录屏
18. GSB 结论
19. GSB 理由
20. 有效性
21. 备注（选填）

除环境可复现等级和备注外，其余字段均为必填。任务难度只能为困难或地狱。Harness 使用实际值，只能为 Claude Code 或 Codex CLI。有效性只能为有效、作废-工程故障、作废-环境未重置、作废-其他。

## 运行与快照

- A、B 使用两个不同容器和两个不同 SessionID。
- 镜像、API Key、模型配置、max context token、Harness、Harness 版本、机器、操作系统和 User Prompt 保持一致。
- 全程使用 auto 模型，max context token 固定为 1000000。
- 两次运行共用一个初始环境快照。
- 远端仓库只有主分支 main 或 master，以及大写 A、B，共三个分支。预检必须读取远端实际引用，确认 `refs/heads/A`、`refs/heads/B` 存在且分别指向登记的 A、B 产物 SHA；小写或其他别名不算通过。
- A、B 产物各自使用完整 40 位 SHA 的 commit permalink，且产物提交的直接父提交必须是初始环境快照。
- A、B 轨迹各提交一个不超过 27 MB 的 JSONL 文件。
- A、B 录屏各提交一个 mp4、mov、webm 或 m4v 文件，不超过 500 MB。

## GSB 审核

结论只能为 A_better、same、B_better，对外分别写为 A 更好、Same、B 更好。

理由至少 60 个汉字，并满足：

- A 和 B 分别说明，不能只写胜方；
- 同时覆盖执行过程和最终产物；
- 过程问题说明触发节点、实际行为和业务影响；
- 产物问题引用真实文件名、函数、命令、测试、报错或未实现需求；
- 说明最终偏好及权衡；
- Same 明确写出等价点，或哪些优缺点相互抵消；
- 不考虑推理时长、网络波动和部署导致的无故截断。

用户已明确允许 AI 分析轨迹、产物并生成 GSB。输出理由不得出现“作为 AI”“根据上述分析”“综合评估”等 AI 式前言、固定标签、模板化分点、机械总结或虚构的亲身体验。内部保留 AI 评价来源和证据哈希，提交字段只保存自然、具体、可核验的理由。

## 质检

正式导出前核对字段完整性、枚举、两个不同 SessionID、单轮限制、Prompt 一致、A/B 独立容器、三个远端分支、三条快照 URL 的仓库和 SHA、两个产物的直接父提交、轨迹与录屏文件、当前证据对应的 GSB 评价。工程故障或环境未重置时标记作废，不硬写有效 GSB 结论。

批量审核逐题读取冻结的 A/B 轨迹和代码产物并形成一条 GSB；证据哈希和审核模型均未变化时复用当前结果。单题审核能力始终保留，可对指定题独立生成或强制重新生成。批量汇总不得把跳过或失败的题伪装成已审核。
